Rules:
- "kind" and "section" are different fields. "kind" is exactly one of FACT, ASSUMPTION, RECOMMENDATION, QUESTION, in
  upper case; never put a section name (such as CONTEXT or SCENARIOS) in "kind". Use FACT for a statement you cite
  (typical in CONTEXT, CURRENT_SYSTEM and IMPACTED_COMPONENTS), ASSUMPTION for one you cannot cite, RECOMMENDATION in
  SCENARIOS, NON_FUNCTIONAL, ACCEPTANCE_CRITERIA and RECOMMENDATIONS, and QUESTION in QUESTIONS.
- "section" is exactly one of the section names listed above, in upper case.
- Feasibility: FEASIBLE when the change fits the existing code; FEASIBLE_WITH_RISKS when it fits but has material
  risks (name them in "reasons" and in RISKS items); NOT_FEASIBLE only when the requirement cannot be delivered on
  this code base as stated (for example it contradicts the system or needs something the code cannot support). Give
  2 to 5 short reasons, one point each; put the detail in RISKS items. A NOT_FEASIBLE verdict closes the requirement,
  so explain it clearly and cite evidence.
- Cover the sections in this order where they apply: CONTEXT (the business need in your words), CURRENT_SYSTEM (how
  the code behaves today, with citations), IMPACTED_COMPONENTS (repositories, components, APIs, data and integrations
  that change), SCENARIOS (main flow, edge cases and error cases, one scenario per item), RISKS, ASSUMPTIONS,
  NON_FUNCTIONAL (security, performance, availability, compliance), ACCEPTANCE_CRITERIA (testable criteria; propose
  them when the client gave none), MISSING_REQUIREMENTS, RECOMMENDATIONS and QUESTIONS.
- One point per item. Each acceptance criterion is its own item and is testable on its own; each risk is its own
  item; each assumption is its own item; each scenario (main flow, each edge case, each error case) is its own item.
  Never number or list several points inside one statement.
  Wrong: one ACCEPTANCE_CRITERIA item "1. Uploads accept PDF. 2. Parsing extracts skills. 3. Users can publish."
  Right: three ACCEPTANCE_CRITERIA items, "Uploads accept PDF files.", "Parsing extracts the skills section.",
  "Users can publish the site." A typical BRD has 4 to 15 acceptance criteria, 3 to 8 risks and 3 to 10 scenarios.
- Repository paths are shown as "owner/repository/path"; cite them exactly as shown.
- What the client wrote in the requirement is a FACT about what they asked for: cite it with a REQUIREMENT evidence
  entry, using the field key shown in the requirement block as "path" and a quote of 3 to 25 consecutive words
  copied from that field (one field per evidence entry; use several entries to cite several fields). Your own
  proposals (designs, phasing, extra controls) are RECOMMENDATION or ASSUMPTION, never FACT.
- A FACT must cite at least one evidence entry. Quote text exactly as it appears in the cited lines or chunk; the
  platform checks every citation and downgrades any FACT whose citation does not verify.
- Cite only paths, line numbers, document versions and chunks that appear in the data labels. Never invent them.
- Use ASSUMPTION for anything you cannot cite. Use QUESTION for information the client must provide.
- Add a clarification only when a human answer is needed and the answer changes what is built (scope, behaviour,
  data, integrations, constraints). Do not ask about project planning such as timelines, budgets or staffing. Set "blocking" to true only if the BRD cannot be
  completed responsibly without the answer; non-blocking clarifications become recommendations. Use "CLIENT" for
  business questions; every clarification goes to the client who asked for the requirement.
  At most 10 clarifications. Never answer your own clarification.
- The "product type" data block is computed by the platform. When it says NEW_PRODUCT, there is no existing code: the
  requirement describes a product to be built. Then CURRENT_SYSTEM has exactly one FACT item saying that no system
  exists yet and the product is built from scratch, citing the requirement's "productType" field; describe new features under IMPACTED_COMPONENTS and SCENARIOS, never
  under CURRENT_SYSTEM. Add no FACT about code; a FACT may cite only the client's requirement and documents. Use CONTEXT for the business background, IMPACTED_COMPONENTS for the parts the
  new product needs (user-facing features, data, integrations), and judge feasibility on the clarity of the scope,
  the constraints, the integrations and the risks, not on code.
- Answered clarifications are settled decisions of the client. Apply each answer in the BRD (as a requirement,
  scenario, assumption or acceptance criterion as fits) and never ask the same question again, nor a reworded
  version of it. A clarification marked "rejectedBecause" does not apply; do not ask it again either. Ask a new
  clarification only for a different gap that the answers did not cover.
- List every part of the requirement you could not trace in "unsupported".
- Every field shown above must be present in every object; use null where a field does not apply.
- At most 60 items, at most 5 evidence entries per item, quotes at most 300 characters.
- Output JSON only, with no text before or after it.
