# Architecture Decision Records: Owner Decisions of 2026-11-08

Each ADR records how an owner-approved decision was built. The decisions themselves are owner decisions; the design choices inside them are the implementer's. They are listed in `../decision-register.md` §14 as D-R8-xx. All ADRs have status **Accepted (implemented on `feature/mvp-production-readiness`, local, not pushed)**.

---

## ADR-01 Provider-neutral model gateway with hosted adapters (O-01)

**Context.**
- The gateway (TDD 13) already isolates providers behind `ModelProvider`.
- O-01 approves OpenAI and Anthropic adapters and a benchmark, but no winner.

**Decision.**
- Two adapters, `AnthropicModelProvider` (`POST /v1/messages`) and `OpenAiModelProvider` (`POST /v1/chat/completions`).
- They use raw HTTPS (JDK `HttpClient`), not vendor SDKs, so no new dependency is added.
- They share `HttpModelProviderSupport`: HTTPS-only base URL (loopback HTTP only with a test flag), timeouts, and mapping of HTTP status to gateway failure kinds.
- Keys come only from `SecretsProvider` (`llm.anthropic-key`, `llm.openai-key`) and are never logged.
- The selection is `sdlc.model.provider`. Its default stays `none`, so no data leaves the platform until the owner selects a provider.
- A separate command line, `ProviderEvaluationMain`, runs dataset `ba-benchmark-v1` against both providers with the production Phase B prompt. It reports measurements only.

**Consequences.**
- Adapter tests run against a loopback mock (`HostedProviderAdaptersTest`). This proves request shape and error mapping, **not** real provider behaviour.
- The evaluation was not executed: no credentials. Provider selection remains with the owner.

## ADR-02 Envelope encryption behind a KMS boundary; secrets provider; fail-closed production (O-12/C-13)

**Context.**
- One static AES key from the environment encrypted every object.
- There was no secret abstraction.

**Decision.**
- `KeyManagement` port with a `LocalKeyManagement` implementation.
- New objects use format **SDE2**: a fresh 256-bit data key per object (AES-GCM), wrapped by the key-encryption key, with the tenant and object key as associated data. SDE1 objects remain readable.
- Reads and deletes check the tenant.
- `SecretsProvider` resolves a secret name to `SDLC_SECRET_<NAME>` (environment) or to a file under `/run/secrets` (`sdlc.secrets.provider=file`).
- `ProductionConfigurationValidator` refuses to start the API or worker with `sdlc.environment=production` when any of these holds:
  - the KMS is local;
  - secrets come from the environment;
  - extraction is enabled without a required sandbox;
  - cookies are insecure;
  - no alert channel is configured.
  It reports only the names of the failed checks.

**Consequences.**
- **No managed KMS adapter exists.** Any provider value other than `local` refuses to start, so production cannot start until an adapter for the chosen platform (O-07) is written and verified.
- There is no S3-compatible object-store adapter either; the encrypted file store is development-grade.
- Key rotation is possible by re-wrapping data keys, but no rotation command exists.

## ADR-03 Two-person, time-limited, single-use production bootstrap ceremony (O-13)

**Context.**
- `bootstrap-admins` (mutual approval written by one operator) is acceptable only for development and test.

**Decision.**
- `bootstrap-ceremony-open` requires two things:
  - the configuration flag `sdlc.provisioning.production-bootstrap.enabled`;
  - an operator authorisation whose SHA-256 matches `...authorization-sha256` (the authorisation is read from stdin and never stored).
- It names two existing staff members and a purpose (INITIAL or RECOVERY), and lives at most 24 hours. Only one ceremony may be OPEN.
- Each participant approves with their own password (stdin) and a current TOTP code.
- When both have approved, the grants are written, bound to the ceremony (`staff_capability_grant.ceremony_id`). The ceremony becomes COMPLETED and is final.
- Expired ceremonies become EXPIRED.
- A database trigger refuses any bootstrap grant without a completed two-approval ceremony.

**Consequences.**
- Recovery (both administrators lost) is the same ceremony with purpose RECOVERY and a new operator authorisation.
- The TOTP code passes as a command argument (SR-M4-2 residual).

## ADR-04 Extractor sandbox with kernel limits and network namespace (O-15)

**Decision.**
- The extractor stays a separate JVM subprocess. It runs:
  - with a cleared environment and a per-job working directory;
  - under `prlimit` (CPU seconds, maximum file size, 256 files, no core dumps);
  - with `sandbox=unshare-net`, inside `unshare --user --map-root-user --net`, so it has no network.
- A startup probe checks that the sandbox works.
- With `sandbox-required=true`, a failed probe makes extraction defer with `EXTRACTION_SANDBOX_UNAVAILABLE` instead of running without isolation.

**Consequences.**
- `ExtractorIsolationTest` ran in this container (not skipped). With a probe program it shows: no network inside the sandbox (outside, the same probe has network), an empty environment, and the file-size limit enforced. The CPU and file-count limits are configured but not asserted by a test.
- There is no mount namespace, seccomp filter or separate container. The process can still read files readable by the worker's user: a **residual risk** for real client documents.

## ADR-05 Closure record, retention clock and tenant soft deletion (O-25)

**Decision.**
- Closure is an immutable `requirement_closure` row, written once by the worker after an eligibility check (D-R8-03).
- Retention counts from `closed_at`, with defaults 30/30/365/365/365 days (snapshot, extracted text, document, BRD, audit). Logs (90 days) belong to the log platform.
- Tenant deletion is soft and two-person: a request, verification, then approval by a different staff member with `TENANT_DELETE` for that tenant.
- The tenant becomes DELETED; sessions and jobs stop; nothing is physically deleted. Restoration uses the same path.
- Database guards:
  - tenant status changes only inside an executed request in the same transaction (`executed_txid`);
  - the retention login lost UPDATE on tenant status;
  - retention skips DELETED tenants.

**Consequences.**
- Physical tenant deletion no longer exists. A later purge after soft deletion would need its own owner decision.
- SHARED_WITH_CLIENT is not closed, so released requirements are never purged until a completion state is decided.
- Legal hold is not supported.

## ADR-06 Manual release and security-scan release gate (O-16, O-03)

**Decision.**
- Release is a recorded `release_approval`: a staff member with `RELEASE_APPROVE` gives the version, the expected content hash, the expected commit SHA and a reason.
- A trigger enforces separation of duties: not the internal approver, not a correction author.
- The worker consumes `ReleaseApproved`, re-checks every gate in `ReleaseGates`, and only then performs T25.
- Gates:
  - the version is current and APPROVED_INTERNAL;
  - the approval is VALID;
  - the input set is unchanged;
  - no clarification is open;
  - a passed `SECURITY_SCAN` exists for each required kind (default SECRET), with no finding at or above the blocking severity (default HIGH).
- Scanners use a `SecurityScanProvider` port with normalised findings.
- A built-in secret scanner masks evidence and fingerprints it. Kinds with no configured product report UNAVAILABLE, which fails the gate.

**Consequences.**
- Dependency and SAST scanning stay unavailable until O-03 names products; requiring them blocks every release.

## ADR-07 Change requests with immutable approved scope versions (C-09)

**Decision.**
- `change_request` moves from SUBMITTED to ASSESSED to AWAITING_CLIENT_DECISION, then to ACCEPTED, DECLINED or WITHDRAWN.
- Who acts:
  - the requirement owner submits;
  - `BUSINESS_ANALYST` assesses;
  - a different `BUSINESS_REVIEWER` reviews;
  - a tenant Client Approver (not the submitter) decides.
- Each acceptance creates an `approved_scope_version` (immutable, sequential) and starts T27.
- `/client-changes` now creates a change request instead of performing T27 directly.

**Consequences.**
- The C-18 conflict is resolved by disclosure: the approver sees only the change request (requested change, assessment, diff), and only once it awaits their decision.

## ADR-08 Prioritised scope diff (C-16)

**Decision.**
- `ScopeDiff` compares scope fields between the approved and proposed scope versions.
- Default priorities:
  - **Critical:** security terms in the old or new text, or removal of acceptance criteria;
  - **High:** business objective, acceptance criteria, integrations;
  - **Medium:** functional description, expected outcomes, non-functional constraints;
  - **Low:** title.
- The assessor may change a priority with a reason before review (`change_request_diff`).

**Consequences.**
- The default mapping is an implementer choice and can be adjusted by the PO without a schema change.

## ADR-09 Bounded retry, operator retry through T26, feature-flag acknowledgement (O-27, O-08)

**Decision.**
- Retry:
  - `job_type.max_retry_seconds` bounds automatic retries in time as well as count (`RETRY_WINDOW_EXCEEDED`);
  - backoff keeps jitter; lease epochs still fence stale workers;
  - an operator with `JOB_RETRY` and an assignment for the tenant may retry a dead **BA analysis** job of a FAILED requirement through T26, giving a reason;
  - permanent failures are refused.
- Feature flags:
  - flags have per-environment values and an append-only change log;
  - a change must be acknowledged by a different operator with `FEATURE_FLAG_ACK`;
  - protected flags cannot be changed through the API.

**Consequences.**
- No generic or cross-tenant job retry exists.
- The API never reads job payloads; it reads only the content-free `app.dead_job` view.
